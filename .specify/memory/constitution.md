# LabLog Constitution

## Core Principles

### I. The Model Is Never Trusted (NON-NEGOTIABLE)

Tool arguments produced by a language model are untrusted input and MUST be treated
exactly as hostile user input is treated.

- Every state change MUST cross exactly one code path: authenticate → authorize →
  validate structurally → validate semantically → write → audit → return. There MUST NOT
  be a second write path.
- Structural validation (types, required fields, enums) is NOT sufficient. Every
  mutation MUST additionally verify its arguments against stored reality: that the named
  entity exists in the named parent, that numeric values are finite, that units resolve,
  and that the target is in a state that accepts the change.
- Authorization MUST be an explicit ownership check in application code, performed once
  before dispatch. Where the backend holds a credential that bypasses row-level
  security, the database enforces nothing on that path and application code is the only
  control present.
- All timestamps MUST be generated by the server. No tool argument model may declare a
  time field; a supplied time MUST be ignored rather than validated.
- Unresolved ambiguity MUST produce a question, never a record. Where a critical field
  is missing or resolves to more than one entity, the handler MUST return a specific
  error carrying the valid alternatives, so the agent can ask rather than guess.
- Values reported back to the user MUST be the values actually stored, not the values
  requested. Confirming what was asked for rather than what was written is a failure
  that presents as success.

**Rationale**: This is the product. A voice notebook that silently guesses is worse than
no notebook, and "the model proposes, the backend disposes" is the only claim that
distinguishes this system from a transcription toy. Every other principle exists to keep
this one true.

### II. The Record Is Append-Only

Stored laboratory data MUST NOT be destroyed or rewritten in place.

- Corrections MUST supersede: insert a new record carrying the correction reason, then
  mark the prior record as superseded by it. Prior values MUST remain retrievable after
  any number of corrections.
- A correction MUST NOT create a first record. Where there is nothing to correct, the
  call MUST be rejected.
- Every mutation MUST append an event row describing what changed, which entity it
  affected, who caused it, and which voice session produced it — written in the same
  transaction as the change itself.
- The invariant `every data row has at least one corresponding event row` MUST hold at
  all times and MUST be directly assertable by query.

**Rationale**: Append-only correction is what separates a laboratory record from a
spreadsheet, and it is a scientific-integrity requirement in the real domain. The event
trail is also the only mechanical proof that no write path bypassed Principle I — if the
invariant holds, the dispatcher is the sole writer.

### III. Trust Boundaries Are Structural, Not Procedural

The separation between privileged and unprivileged code MUST be visible in the directory
tree and checkable by a machine.

- Credentials capable of bypassing per-user access control — service-role database keys,
  third-party API keys, JWT signing secrets — MUST exist only in the backend service and
  MUST NOT appear in any frontend file, environment variable, build artifact, or API
  response.
- The browser MUST hold only the anonymous database key and the signed-in user's own
  session. Any credential it receives for a third-party service MUST be single-use and
  short-lived, and MUST be minted only after the requesting user has been authorized.
- Row-level security MUST be enabled and owner-scoped on every table. It protects direct
  browser reads and subscriptions; it MUST NOT be relied on for backend writes.
- The credential separation MUST be enforced by an automated check in continuous
  integration, not by reviewer discipline.

**Rationale**: A security property that depends on everyone remembering it will fail the
first time several agents work in parallel. Making the boundary a property of the
repository layout means it can be verified by grep instead of by trust.

### IV. Verified Inputs and Single Sources of Truth

Code MUST NOT be written against a remembered, inferred, or reconstructed interface.

- External wire formats MUST be verified against live vendor documentation before any
  code depending on them is written, and the verified form MUST be transcribed into a
  contract document that implementers read instead of the vendor documentation.
- Where the same definition drives both what an external system is told and what our
  code enforces, there MUST be exactly one declaration, with all other forms derived
  from it. Hand-maintained parallel definitions are prohibited because their divergence
  is silent.
- Before concurrent work begins, the interfaces between work streams MUST be frozen as
  written contracts with committed example fixtures. Each file MUST have exactly one
  owning stream.
- An implementer who believes a frozen contract is wrong MUST stop and escalate with
  evidence. Editing the contract unilaterally, or working around it locally, is
  prohibited.

**Rationale**: The project's initial brief contained thirteen errors in a reconstructed
wire protocol, four of which fail silently at runtime and present as vendor flakiness.
Verification before implementation is cheap; debugging a silent protocol mismatch under
deadline is not. The contract-freeze rule is what makes parallel work real rather than
nominal — streams depend on documents, never on each other's unfinished code.

### V. Claims Require Evidence

No assertion of correctness, reliability, or completion may be made without a
reproducible artifact behind it.

- A phase MUST NOT be declared complete until its definition of done has been executed
  and its output observed. "It looked right" is not a result.
- Every reliability figure shown to any viewer MUST be produced by the evaluation
  harness in this repository and MUST be reproducible by running it. Figures MUST NOT be
  estimated, rounded up from memory, or asserted without measurement.
- The evaluation harness MUST exercise the real validation handlers. Evaluating a mock
  of the validation layer measures nothing, because the validation layer is the claim.
- Measured failures MUST be reported alongside measured successes. A result set showing
  only passes is not evidence.
- The system MUST NOT report a save, a completion, or any other outcome that did not
  demonstrably occur. Where an operation's outcome is unknown — a dropped connection
  mid-call — the system MUST reconcile against stored state rather than assume either
  result.

**Rationale**: Unmeasured reliability claims are the weakest part of any demonstration
and the cheapest thing to fix. A figure that cannot survive "how did you measure that?"
discredits every other figure beside it.

## Scope and Technology Constraints

**Scope is a contract, not a starting position.** The in-scope feature set recorded in
`specs/001-lablog-voice-notebook/spec.md` is binding. Deferred features MUST NOT be
built, and an implementer asked to add one MUST decline and point at the scope record.
Scope may be widened only by amending the specification first — never mid-implementation.

**Locked technology decisions.** The following MUST NOT be revisited without an
amendment recorded under Governance:

- Speech recognition, turn detection, reasoning, tool selection, speech synthesis and
  barge-in are owned by the external voice agent platform. Audio MUST travel directly
  between the browser and that platform and MUST NOT be proxied through our backend.
- No agent-orchestration framework. The reasoning loop does not run in our process;
  our backend receives a validated function call and returns a row, which is a
  dispatcher. Validation is performed by typed models and routing by plain functions.
- Conversational context is ordinary database state — read from storage, injected into
  the session at start, and re-read inside every handler. There MUST be no
  framework-held agent memory that can diverge from stored truth.
- Tool calls MUST be returned through the authenticated browser rather than invoked
  directly against our endpoints by the platform, so that each call carries the
  end user's own credential. The model MUST NOT be permitted to assert user identity
  through a tool argument.
- No single session configuration may expose more than twelve tools. A tool set
  may be split into state-scoped profiles drawn from one registry (for example: no
  experiment open, or an experiment bound). Raising any profile's size requires an
  eval run showing that profile's tool-selection accuracy is no lower than the prior
  baseline on the same model. *(Amendment A-1, 2026-09-26.)*

**Deliberate non-goals.** Unit conversion, cross-browser audio support, organizational
administration, permission matrices, instrument integration, and document ingestion are
out of scope. A partial implementation of any of these is worse than none, because it
handles the cases it knows and silently mishandles the rest.

## Development Workflow

**Version control.** The project MUST be a git repository, and work MUST be committed
after each working increment with a descriptive message. This is a prerequisite for
parallel work, not a convenience: file ownership, contract freezing and integration
gates are all unenforceable without it.

**Phase discipline.** Work proceeds by phase. Each phase has a written definition of
done which MUST be executed and observed before the next phase begins. Riskiest
unknowns are resolved first; a phase whose result could change the plan MUST be
scheduled before the work it could invalidate.

**Parallel execution.** Concurrent work streams MUST operate under exclusive file
ownership and frozen contracts (Principle IV). Streams integrate at named gates with
defined entry conditions and a single observable outcome each; between gates they MUST
NOT block on one another. A stream that cannot proceed without another stream's code has
a missing contract, not a scheduling problem.

**Contract amendment procedure.** When a frozen contract is found to be wrong:
(1) the discovering implementer stops and reports the divergence with evidence;
(2) the contract is amended and the change recorded in its changelog;
(3) every stream listing that contract as a dependency is notified before continuing.

**Testing.** Validation logic MUST be unit-testable without a live database, by
accepting its data client as a parameter rather than constructing one. Evaluation
scenarios MUST be written alongside the capability they test, not deferred to the end.

**Rejections must not corrupt.** For every rejected operation, tests MUST assert not
only the returned error but also that no row was written. A handler that validates after
writing satisfies every response assertion while corrupting the database.

## Governance

This constitution supersedes other working agreements, including the standing
instructions in `LabLog_Implementation_Plan.md` §17, from which it is derived. Where the
two disagree, this document governs and the source brief SHOULD be corrected.

**Amendment procedure.** Amendments MUST be made by editing this file, MUST state the
rationale for the change, and MUST be recorded as a commit. An amendment that removes or
redefines a principle MUST also identify the artifacts that relied on it.

**Versioning policy.** Semantic versioning applies to this document:

- MAJOR — a principle is removed or redefined in a backward-incompatible way, or
  governance rules change materially.
- MINOR — a principle or section is added, or existing guidance is materially expanded.
- PATCH — clarification, wording, or typo correction that does not change meaning.

**Compliance review.** Every implementation plan MUST include a Constitution Check that
evaluates the work against these principles before design begins and again after design
completes. Violations MUST be either corrected or explicitly justified in a complexity
record naming the simpler alternative that was rejected and why. An unjustified violation
blocks the plan.

**Precedence.** Principle I is non-negotiable and MUST NOT be traded against schedule.
Where deadline pressure conflicts with any other principle, the correct response is to
reduce scope under the Scope and Technology Constraints section, never to relax a
principle.

**Runtime guidance.** Implementers follow the current feature's plan, contracts and data
model under `specs/` for day-to-day direction. Those documents MUST conform to this
constitution; where they conflict, this document governs.
